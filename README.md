# bhbench — 安卓电池等效容量与健康度测量

用一次受控放电，算出手机电池**真实放出了多少电荷**，再和标称容量比对。
不看厂商那个百分比——那是各家算法的加权结果，权重不公开，跨品牌没法比。

手机上跑，不需要电脑、不需要 root。

```
等效容量   6561 mAh
标称容量   7000 mAh
健康度     93.7%   良好
数据来源   系统库仑计差值
```

> 这组数来自 2026-11-04 一次 17h15m 的真机记录（96% → 9%，156 个采样点）。
> 同一次数据用 v0.1 的电流积分算出来是 **8959 mAh / 128%「良好」**——假的。
> 修法见 [「v0.2：为什么之前会算出 9000 mAh」](#v02为什么之前会算出-9000-mah)。

---

## 两种用法

| 方式 | 适合谁 | 需要什么 |
|---|---|---|
| **装 App**（主推） | 普通使用：自己测自己的手机 | 一个 APK，装完拔线就能跑 |
| **adb 采集**（进阶） | 批量测多台、无界面环境、开发调试 | 电脑 + adb + 编译好的二进制 |

App 和 adb 走同一套数据源、同一套算法，CSV 格式一模一样，
所以两边结果可以互相验证。

## App 怎么用

```bash
adb install -r bhbench.apk
```

或者直接把 `bhbench.apk` 传到手机上点开安装。

**推荐流程：一次记录覆盖放电和充电**

1. 打开 App，填厂商标称容量，点**开始记录**——之后一直记录，中途不用停
2. 正常用手机。电量到 15% 左右 App 会弹提醒（也可以自己留意）
3. 插上原装充电器充到 100%，期间不用管 App
4. 拔线，点**分析最新**

**充电时也能开始。** 采样不区分充放电，只要点开始就在记：
满电拔线用下去记的是放电段，插着充电器记的是充电段。
主界面实时面板会把两段已记时长分开显示，不用猜 App 到底在记什么。

一份 CSV 里同时有放电段和充电段，分析器会自动挑合格的那一段：

- 从 100% 用到 15% 的放电段**不完整**（没放到关机），会被跳过
- 改用 15%→100% 的充电段，按 SOC 跨度折算

**为什么不等到自动关机**：手机一关，App 就没了；插上充电器重新开机后需要解锁、
找图标、再点开始，这中间已经充进去几个点，误差反而更大。留 10–15% 插电是更优解。

如果你愿意完整放电（更准，不需要折算），就充满、拔线、用到自动关机，
中途同样不要停。放电段不需要任何假设，精度最高，代价是占用几个小时的使用时间。

测试期间可以正常用手机。负载波动、息屏、进 Doze 都不影响结论——
净电荷取自硬件库仑计的首尾差，不是对瞬时电流做积分。结果只代表你自己的使用强度。

结果页会给出：大号健康度 + 评级、**电量变化图**、三张指标卡（等效容量 / 标称 / 时长）、
明细（数据来源、本次净电荷、折算后容量、放出能量、平均电压电流、峰值温度、
SOC 区间与跨度、采样质量、两条算法的交叉校验），以及这次测量存在的问题清单。
数据不足或结果超出物理合理区间时不给百分比，直接写「数据不足」/「数据异常」。

底部「导出原始数据」走系统文件选择器，不申请存储权限——导出是附带功能，
主要出口是这个结果页。

### 电量变化图

系统「电池使用情况」里那张图，本质就是 SOC 随时间的折线。结果页用自己采的点
画同一张图，但叠了两条参考线，让它变成能判断东西的工具：

| 线 | 是什么 | 看它做什么 |
|---|---|---|
| 粗实线 | 实测 SOC（厂商报的百分比，= 系统那张图） | 这就是系统图的复现 |
| 灰虚线 | 最小二乘直线（时间加权） | 「按使用时长匀速掉电」的理想假设 |
| 橙细线 | 库仑计反推的 SOC（硬件累加的真实电荷） | 检验系统百分比有没有被平滑 |

- **实线与虚线的距离** = 这段时间耗电比平均快还是慢
- **实线与橙线的距离** = 厂商的百分比和真实电荷差多远。实测那份真机会话里
  最大差 7.3 个百分点，说明系统在低电量段做过平滑，拿它当电荷量会算错
- **灰色竖带** = 这段时间没采到点（息屏进 Doze 后被系统拉长），曲线在那里是
  直线连过去的，不能当真实读数

图下面会写：本次几小时掉几个点、按这个跨度满电可用多久、拟合斜率与 R²。
R² 低于 0.5 会明说「这段时间强度忽轻忽重，直线只代表平均」——不假装曲线是直的。

**为什么回归要按时间加权**：Doze 会把 7 小时的采样压成两三个点。按点等权做回归，
那 7 小时只算了两三票，而密集采样的活跃期每小时好几票 —— 拟合出的斜率会被
活跃期带跑。同一份真机数据三个数：端点斜率 5.04 %/h、等权回归 3.51、
时间加权 3.99。加权不是把数字改大，是让它别再被采样密度左右。

「满电可用多久」用的是实测跨度（本次用了这么久、掉了几个点），不是拟合斜率 ——
R²=0.78 的弯曲线拟合给出 4.0 %/时，而这次实际是 17 小时掉 87 个点。
用户关心的是后者。

### 用每次记录反哺

两个数会攒起来（各留最近 12 次）：

- **R²**：拟合贴合度。低于 0.9 说明采样太稀或使用强度太跳
- **耗电率 %/h**：这台机器、这个人的典型强度

下次打开结果页，会拿本次的数和自己的历史中位数比：

```
曲线贴合度 0.982，你之前 3 次的中位数是 0.966（+1.6 个百分点）；
这次 4.1 %/时，你自己历史平均 3.8 %/时（快 8%）
```

同一个 CSV 只记一次，反复打开不会把统计刷成同一个数。

### 自适应采样

默认 5 秒一个点，但电量百分比和库仑计都没动时会逐步放宽到 30 秒，一动立刻
回到 5 秒；充电时用 15 秒打底。主界面会显示当前间隔，放宽了会写明原因。

这么做是安全的：最终容量取库仑计首尾差，是硬件累计量，跟采样频率无关；
采样疏只会让曲线粗一点，不会让算出来的 mAh 变。

### 息屏放电时采样一定会断档

这是这套方案最硬的一个限制，先说清楚。

放电测试要跑一整晚，手机息屏进 Doze 后后台进程会被冻住。实测（Xiaomi
25113PN0EC / Android 17）：点开始记录、息屏，**8.3 秒**后 `PARTIAL_WAKE_LOCK`
就被系统强制释放，进程随即被冻结，6 分 14 秒后才出现第二个采样点。logcat 里
是 MIUI 的 `PowerKeeper: reason=freeze_able`。

前台服务只能保证进程不被杀，保证不了线程被调度；`PARTIAL_WAKE_LOCK`、
`HandlerThread`、`setAndAllowWhileIdle` 看门狗、`specialUse` 前台服务类型这几条
都试过，在这台机器上挡不住 PowerKeeper，已全部撤掉，不留无效代码。国产 ROM 的
「省电策略 → 无限制」和「自启动」能在一定程度上缓解，但那是系统设置，App 无权改。

**所以息屏放电段的采样点必然稀疏、空档必然存在**，这部分数据只能用首尾库仑计差
算容量（它是硬件累计量，与采样间隔无关），不要指望在放电段拿到密集曲线。

充电段不一样：插着电时手机不会进 Doze，可以拿到 5 秒一个点的连续数据——
这也是「电流积分到底准不准」那个结论只能在充电段验的原因。

### 历史记录

主界面「历史记录」列出所有会话文件，每条直接显示结论摘要——不用点进去才知道
哪次是白跑的：

```
2026-11-04  00:33    放电段 · 健康度 93.7% · 6561 mAh · 17h15m
2026-11-03  22:04    充电段 · 时间太短 · 87 mAh · 6m
2026-11-03  21:40    空文件 · 没有数据
```

短记录会写明差在哪（时间太短 / 没充到 100% / 不是满电开始 / 没放到低位），
而不是笼统一句「数据不足」。在这里可以：

- **勾选后导出**：一份走保存对话框，多份让你选一个文件夹、一次全写进去
- **勾选后删除**：先列清楚要删哪几条再确认；正在记录的那份会被跳过，删不掉
- 顶部显示总占用，卸载 App 会连同这些文件一起消失，要留的先导出去

App 里做了三件事保证数据能用：

- **前台服务 + 常驻通知**，避免跑几小时被系统或 ROM 的省电策略杀掉
- 只读公开 API（`BatteryManager` 的库仑计和电池广播），不 root、不碰 sysfs
- 每 5 秒落盘一次。⚠️ 息屏进 Doze 后这个周期会被系统拉长到几十分钟甚至几小时
  （真机见过 7.4 小时空档），这是 Android 的省电行为，App 改不了；
  但因为每个采样点都带库仑计读数，**结果不受影响**，见下节

### 充电器体检

电池那套测「电池还能装多少」，这一页测「充电器能给多少」。两件事共用同一套
BatteryManager 数据源，但关心的量完全不同。

200 ms 一个点、跑 90 秒。为什么要这么密：快充协商是**瞬间**的事，PD 从 5V 切到
9V 就是几十毫秒，5 秒一个点只能看到结果、看不到过程，而过程里才有协议的证据。

**先说物理边界，这个边界决定了这个工具能说什么：**

```
手机能读到   →  电池侧电压电流（BatteryManager）
手机读不到   →  USB 输入侧 VBUS / IBUS（sysfs 被 SELinux 封，App 没 root）
中间还隔着   →  充电管理芯片，效率 85–92%
```

所以「峰值功率」是电池吃进去的功率，不是充电器标称输出。好在评测充电器要的
正是这个：标称 120W 的充电器，能不能让这台手机真的跑到极限、能跑多久、
热了掉不掉队 —— 全在这条曲线上。

#### 没插充电器时什么都不测

这里踩过一个真 bug：放电时 `CURRENT_NOW` 是**负值**，而功率算的是
`abs(V×I)` —— 绝对值一取，放电电流就变成了一个看着很正常的「充电功率」。
`analyze()` 又只看 `peakW > 0.5` 就判有效，于是**不插充电器跑满 90 秒也能
出一份峰值 / 稳态 / 充入 Wh，还能存进档案跟真充电器比**。

现在采集侧和分析侧各挡一道：

| 层 | 做法 |
|---|---|
| 采集 `ChargerPanel.read()` | 读 `EXTRA_PLUGGED`，没插电直接 `pWatt = 0` |
| 界面 | 大字显示 `—` / 「未连接充电器」；点开始体检直接拒绝 |
| 过程中 | 中途拔线立刻停止，整段作废，不给结果、不给保存按钮 |
| 分析 `ChargerProbe.analyze()` | 先过滤出 `plugged && (charging\|full)` 的点；有效点不足或占比 < 80% 就判无效 |

判据必须同时看 `EXTRA_PLUGGED` 和 `status`：只判电流方向不行（`CURRENT_NOW`
的正负号各厂商实现不统一），只判 status 也不行（拔线瞬间有的 ROM 还留着
`charging`）。`EXTRA_PLUGGED` 是内核直接反映插拔的，最硬。

导出的 `probe_*.csv` 末尾多了一列 `plugged`（0/1）。旧版 7 列 CSV 仍可读，
按 `status` 推断插电状态，不会把历史数据全判废。

#### 协议怎么判断

Android 没有公开 API 能读出 PD / QC / SCP / VOOC。社区里真正能确定协议只有两条路：
**root 后读厂商 sysfs 节点**（高通平台的 `usb/real_type` 直接给 SDP/CDP/DCP/PD/HVDCP），
或者**买个 USB 测试仪**串在中间抓 CC 线报文。主流 App（Ampere、AccuBattery）干脆
不判断协议，只显示电流。

这个工具两条都试：

1. **先读内核节点**（`SysfsProbe`）。能读到 VBUS 就直接给电压档位，
   读到 `real_type` 就直接给类型 —— 这是真答案，不用猜。小米 17 上实测全封，
   换个没封的机型或者用户自己 root 了就能用。
2. **读不到就反推**（`ProtocolGuess`）。电池侧功率 ÷ 0.88 估算输入功率，
   落在哪个区间就对应哪几组「电压×电流」组合，同时看起始阶段有没有功率台阶
   （有台阶 = 发生过协商）。

**反推的置信度最高只给「中」。** 这不是保守，是方法的上限：看不到 VBUS，
50W 可能是 20V/2.5A(PD) 也可能是 11V/5A(SCP)，电池侧分不出来。标「高」就是骗人。

#### 第三方充电器

同一台手机换着充电器测，数字才可比。每次体检可以起名字存下来：

```
小米原装 67W        47.8 / 44.1 W
Anker 65W           46.2 / 45.9 W
车载充电器          18.1 / 17.6 W
```

看三件事：**峰值**（冲不冲得上去）、**稳态**（压不压得住）、**波动**
（输出稳不稳）。标称功率高但稳态掉队的，多半是协议没谈成退回了基础档。

#### 采样抖动

这块单独说，因为它是所有长时间测量的共同敌人。

App 是前台服务，但 Doze 和国产 ROM 的省电策略照样会掐：真机跑 17 小时只拿到
156 个点，最长一次空档 **7.4 小时**。曲线在那里是直线连过去的，不是真实读数 ——
图上用灰色竖带标出来。

结果页现在把抖动量化：

```
采样被系统打断 14 次：正常 5 秒一个点，最坏 1% 拖到 120 秒，最长 7.4 小时
中位 5 秒 / P99 120 秒 / 打断 14 次
```

用 P99 不用 P90：90% 的间隔都正常时 P90 就等于中位数，抖动完全看不见。

**这些都消除不了**，只能如实报告。斜率用时间加权整体拟合（这是对非均匀采样的
正确处理，见上面「为什么回归要按时间加权」），抖动的影响单独摆在明面上。
结果页还会检查 App 有没有被排除在系统省电策略外，没放行就给一个跳转入口。

### 深色模式

主界面「显示模式」可三选一：**跟随系统**（默认）/ **浅色** / **深色**。
长时测量往往一跑十几个小时，系统夜间模式按时间自动切换会让配色中途变掉，
手动锁定就是给这种场景用的。

四个界面和两张图共用一套色板（`Palette.java`）；窗口底色、状态栏图标颜色、
系统对话框由 XML 主题（`values/styles.xml` + `values-night/styles.xml`）负责。
两条通道必须同时切，少一条就会出现「深底 + 深字」。`ThemeMode.java` 统一管，
切换后清空 Activity 栈重开，后退栈里已建好的页面也会跟着重建。

### 系统电池曲线对比（需要接电脑）

树问过能不能把 App 的采样曲线和系统「电池使用情况」里那张图放一起比。
**能，但只能在 PC 侧做** —— App 自己读不到系统电池历史。

设置里那张图的数据来自 `BatteryStatsImpl` 的 history buffer，是 hidden API，
非系统应用没有权限。但 adb 能把它导出来：

```sh
adb shell dumpsys batterystats --history > history.txt
python -m analyzer.system_history \
    --csv data/session_20261104_184944.csv \
    --history history.txt --out compare.svg
```

history 里每行 `11-04 18:00:00.116 008 status=charging ...` 的三位数字就是
电量百分比 —— 和 App 读的是同一个 `BatteryManager.EXTRA_LEVEL`。会话起点从
`session_YYYYMMDD_HHMMSS.csv` 的文件名取，两边对齐到墙上时钟后叠在一张图上。

**真机实测（11-04 那次 18%→100% 充电）**：窗口内系统记了 83 次电量变化，
98.2% 的 App 采样点能匹配到系统曲线，平均偏差 **0.49 个百分点**、最大 1.0 个点
—— 就是 1% 量化分辨率，数值上两条线其实是同一条。

所以这个功能比的不是数值，是**采样时机**：系统按「电量跳 1% / 状态变化」记事件，
App 按固定间隔记，Doze 和省电策略会把 App 的点掐出空档。空档里系统有没有掉电、
App 有没有漏掉台阶，叠起来一眼看得出来。

注意 history 是 **4 MB 环形缓冲**（这台机器 100% used、36 万行），几天的长会话
可能被覆盖；覆盖后脚本会明确告诉你窗口内没有数据，不会编一条线出来。

### 充电器档案

体检页存下来的记录统一在「充电器档案」里管理：按充电器名字聚合，用两条横条
对比峰值与稳态（峰值取最好一次、稳态取平均），能改名、删除、清空、导出 CSV。
同一个充电器多次测会合并成一行，标 `×N`。

### 界面

四个界面共用 `Ui.java` 一套组件（圆角卡片、主/次按钮、分区标题、设置页式的
「左标签 / 右数值 + 细分割线」行）。强调色不写死，从当前主题的
`android.R.attr.colorAccent` 取 —— MIUI / ColorOS / 原生 Android 各给各的主题色，
App 跟着 ROM 走，而不是套一层自制皮肤。按钮上的文字按强调色亮度自动选黑或白。

### 启动唤醒动画

0.5.3 起，从桌面点图标先走 `WakeActivity`：电池从 0 一格格充到**此刻的真实电量**
（`ACTION_BATTERY_CHANGED` sticky 广播读的，不是写死的数），数字跟着跳，充完淡出
进主界面。全程约 1.26 秒，轻点任意处可跳过。低于 15% 用异常色、15–40% 用提醒色，
其余用系统强调色。

独立成 LAUNCHER Activity，而不是在 MainActivity 上盖一层遮罩 —— 只有冷启动
（进程新建、从桌面点图标）才会播；从结果页返回、App 在后台被切回前台，
系统直接恢复原 task，不会重播。动画对象在 `onDestroy` 里 cancel，不留回调；
前台采样服务和它互不相干，正在跑的记录不受影响。

## 为什么不用厂商的健康度

厂商显示的百分比大致由三样东西加权而来：容量衰减、循环次数、内阻上升。
权重各家不公开，还会随系统版本调整。结果就是：

- 同一块电池，A 品牌显示 92%，B 品牌显示 87%，实际容量可能一样
- 换过电池或第三方维修后，百分比可能完全不更新
- 出厂标定和实际容量本来就有 2–5% 的差

所以这个工具绕过所有厂商接口，自己做一次物理测量：从满电放到关机，
记录全程的电荷流出。数据通道按**优先级**选，不是随便挑一条：

1. **库仑计可用且方向单调** → 计数器首尾差（首选）
2. **没有库仑计但采样连续** → 电流梯形积分
3. **没有库仑计且采样稀疏** → 长空档按 SOC 变化估算，并拒绝给健康度

第一条最好：库仑计是硬件累计量，首尾差直接就是放出电荷，既不经过积分，
也不受采样间隔影响。实测这类机器的库仑计约 20–25 秒跳一次。
电流积分会同时算一遍，只作为交叉校验值留在报告里——两条算法偏差超过 10%
就会明确警告，而不是闷声输出一个看起来很像那么回事的大数。

## 三法交叉校验（测试期）

现在有三种独立方法可以算容量，各自假设不同。测试期的目标不是"信哪一种"，
而是**用数据决定哪一种可信**：

| 方法 | 数据来源 | 成本 | 隐含假设 |
|---|---|---|---|
| **A 满电直读** | 充满时的库仑计读数 | 零（充电时自动记） | counter 是实测积分，不是标定常数 |
| **B 放电测量** | 满电 → 低电量的电荷积分 | 几小时使用时间 | 无（这是基准） |
| **C 充电折算** | 低电量 → 满电的充入量 ÷ SOC 跨度 | 一个晚上 | 电荷在 SOC 区间内均匀分布 |

App 会在每次充满时自动落一条快照，所以 A 是白送的；B 和 C 需要你手动开一次记录。

攒够数据后跑：

```bash
python analyzer/compare.py data/session_*.csv --design 7000 --snapshots data/snapshots.csv
```

它会给出三种方法的数值、互相偏差和置信度评级，并回答那个关键问题：

- **A 与 B 相差 < 2%** → counter 可信，以后充满读一次就够，整个流程可以砍到零成本
- **相差 2–5%** → 可做趋势参考，别当绝对容量
- **相差 > 5%** → counter 多半是标定常数，必须靠 B 或 C

置信度规则写在 `analyzer/compare.py` 里，可以直接改：

- B 要求起始 ≥95%、结束 ≤10%、时长 ≥2h，三条全满足才是「高」
- C 的误差模型是 `2% + 30/跨度`，跨度 85% 时约 ±2.4%，跨度 60% 时约 ±2.5%
- A 没有独立判据，只能用「和 B 的偏差」反推它可不可信

**本机已有实测裁决**（2026-11-04，Xiaomi 25113PN0EC）：

```
A 满电直读   4605 mAh   65.8%   低
B 放电测量   6561 mAh   93.7%   高
A 相对 B：-29.8%  → counter 明显偏离实测，多半是标定值
```

三条满电快照（10-28 / 10-31 / 11-03）稳定在 4600 左右，趋势 -0.15%，
几乎是常数。所以**这台机上 A 不能当绝对容量用**，但它不影响 B：
B 取的是同一计数器的**差值**（相对量），A 取的是**绝对值**（受满电重标定影响），
两者可以一个准一个不准。快照继续记，用来看趋势是合适的。

## v0.2：为什么之前会算出 9000 mAh

一次真机记录，正常使用一整天（17h15m，96% → 9%），v0.1 给出
**8959 mAh / 健康度 128% / 评级"良好"**。电池标称才 7000 mAh，
新电池也不可能超 15%，所以这个数一定是算错的。

### 数据长什么样

| 指标 | 值 |
|---|---|
| 采样点 | 156 个 / 17.25 小时（名义 5 秒一次，实际平均 6.6 分钟） |
| 有效覆盖率（间隔 ≤60 s） | **1.2%** |
| 最长空档 | **7.4 小时** |
| 库仑计首尾差 | 6369 → 574 mAh = **5795 mAh** |
| 电流梯形积分 | **9507 mAh**（+64%） |

手机息屏进 Doze 后，前台服务的定时采样被系统批量推迟；醒来那一刻往往是
唤醒/亮屏的高电流。梯形法拿这两个瞬时值去线性外推整个空档：

```
t=2562s  I=108 mA  ──┐
                     │ 间隔 26604 s（7.4 h），积分按平均 205 mA 算 → 1519 mAh
t=29166s I=303 mA  ──┘  而库仑计只掉了 345 mAh（SOC 89%→84%）
```

光这一段就凭空多算 1174 mAh。全天空档累计，把 5795 吹成了 9507。
**库仑计是硬件累计量，和采样频率无关**，首尾一减就是净电荷。

### 修了什么

1. **数据通道优先级反转**：有库仑计且方向单调时一律用首尾差；
   电流积分降级为交叉校验值，偏差 >10% 主动报警。
2. **采样质量成为硬指标**：报告必带有效覆盖率、最长空档、长空档次数；
   没有库仑计又覆盖不足 80% 时，长空档改按 SOC 变化估算，并标「数据不足」。
3. **健康度物理合理性检查**：超出 30–115% 一律「数据异常」，
   绝不再出现「128% 良好」这种结论。
4. **SOC 跨度折算对称化**：96% → 9% 只放出 87% 的电，
   与充电段一样按跨度折算到满电，报告同时给出折算前净电荷。
5. **温度系数 0.008 → 0.002**：每 °C 0.8% 没有依据，
   手机 32 °C 正常工作温度就被凭空折掉 6%；改为 0.2%，`--temp-coeff 0` 可关。
6. **修正列名语义**：CSV 第 7 列是 `BATTERY_PROPERTY_CHARGE_COUNTER`
   **剩余电荷**，v0.1 误命名为 `charge_full_mah`（像"满电容量常数"），
   连合成数据都跟着写成恒定值。现改为 `charge_counter_mah`，
   读端保留旧列名兼容，手机上的历史会话照常能分析。
7. **结果页不再骗人**：数据来源按实际方法显示（旧版把库仑计差值也标成
   「电流积分」），并新增净电荷、SOC 跨度、采样质量、交叉校验、测量结论。

修完同一份数据：**净电荷 5795 mAh ÷ 87% = 6661 mAh，温度归一后
6561 mAh，健康度 93.7%**。App 与 PC 端分别验证，数值一致。

回归锁在 `tests/test_regression.py`（12 项，含这份真机会话的原样夹具）：

```bash
python -m unittest discover -s tests -v
```

## 电流积分到底准不准

真机实测：**不准，而且不是采样率的问题。**

2026-11-04 那次充电（18%→100%，2.45 小时）三角对照：

| 口径 | 数值 | 偏差 |
|---|---|---|
| 库仑计首尾差 | 5635 mAh | 基准 |
| 全段梯形积分（含空档） | 3278 mAh | **−42%** |
| 连续段积分（只看没空档的 45 分钟） | 727 / 1102 mAh | **−34%** |

关键在第三行：那 3 段里 5 秒一个点、**完全没有空档**，积分仍然少算三分之一。
所以问题不在采样疏密——是 `BATTERY_PROPERTY_CURRENT_NOW` 这个读数本身系统性偏
（这台机器充电时约 −25%，逐 3 分钟滑窗都指向同一方向，不是随机抖动）。

库里能查到的旁证：把库仑计首尾差 5635 除以 SOC 跨度 82%，得到 6872 mAh，
与标称 7000 只差 1.8%——**库仑计与 SOC 自洽**，偏的是电流读数那一侧。

因此：

- 容量结论**一律走库仑计首尾差**，它不依赖采样率，也不依赖电流读数的绝对精度。
- 电流积分只当交叉校验，且改用**连续段对账**：把采样按 60 秒阈值切块，只在
  没有空档、且不短于 5 分钟的块里比 `∫I dt` 与 `ΔCC`。这样"采样被打断"
  和"读数本身偏"就分开了，结果页直接给出这两行。
- 想靠积分算出容量，前提是把电流读数标定准（外接电流表或功耗仪对一遍），
  光加密采样没用。

这也是为什么市面上的容量工具基本只用充电段测：不是充电时采样更密，而是
**放电时的电流取决于用户怎么用手机，不可复现**——同一块电池，刷视频和待机
测出来的"容量"能差三成。充电时电流由充电器决定，才有可比性。

还有一层现实原因：放电测试得息屏跑，而息屏后国产 ROM 会冻住后台进程
（见上面「息屏放电时采样一定会断档」），根本拿不到连续采样。充电时手机插着电
不休眠，才有条件密集采样。

## v0.5.5：常亮充电下的积分精度验证

上一节的结论是「充电段连续 45 分钟、5 秒一个点，积分仍比库仑计少 34%」。但那是用**已有数据**做的对账，采样间隔是固定的，没法回答「如果采得更密，积分会不会准」。要回答这个，得先让采样真的连续。

### 为什么是「屏幕常亮」

`v0.5.3-rc2` 试过在息屏放电时用 `PARTIAL_WAKE_LOCK` + `HandlerThread` + 看门狗闹钟 + `specialUse` 前台服务硬扛，结果 8.3 秒就被 MIUI PowerKeeper 收走唤醒锁、冻结进程（[issue #1](https://github.com/SZYTree0312/battery-health-benchmark/issues/1)）。结论是：**App 不能跟 ROM 的省电策略对抗**。

安兔兔的电池损耗测试走的是另一条路。公开可查的用法是：插着充电器、电量别太满、**测试页面保持在前台**、期间不要用手机、充 10 分钟以上越久越准。网上对「要不要亮屏」说法互相矛盾（有说必须亮屏，有说锁屏也行），但真正起作用的不是亮屏这个动作，而是 **Activity 常驻前台 = 进程始终可见** —— Doze 判定「闲置应用」时根本不会把它列进去，PowerKeeper 也无从冻结。

所以这里照做，且只用官方推荐的方式：

- `FLAG_KEEP_SCREEN_ON`：当前窗口可见期间屏幕不自动熄灭。**不需要 `WAKE_LOCK` 权限**，Activity 一离开就自动失效 —— 没有唤醒锁可收。
- 采样跑在**页面自己的 Handler** 上，不碰 `SamplerService`、不起前台服务、不申请任何防冻结权限。rc2 撤掉的东西一件都没回来。
- **一旦主动息屏或切到后台，立刻停止并把本次标记为中断**（`ACTION_SCREEN_OFF` + `onStop` 双保险）。宁可数据短，也不要被冻过的数据 —— 空档恰恰是这个实验最不能有的东西。
- 只在充电段做：插电时手机本来就不进 Doze，且充电电流由充电器决定、可复现；放电电流取决于用户怎么用手机，不可复现。

亮屏本身耗电，但 **ΔCC 和 ∫I dt 量的都是同一段电池侧净电荷**，两条路径同源，比值 k 不受屏幕功耗影响。只是别把这个电流当成「充电器输出」。

### 一次测量回答两个问题

入口：设置 → 测量工具 → 积分精度验证。采样间隔可选 0.5 / 1 / 2 / 5 秒，时长 10 / 20 / 30 分钟。

| 问题 | 做法 |
|---|---|
| 采样加密还有没有用？ | 把**同一段**原始数据抽稀成 1 / 2 / 5 / 10 / 30 秒，各自梯形积分。跨尺度极差 ≤2% 视为收敛 —— 收敛了，采样率就不再是误差来源，偏差只剩读数本身 |
| 偏差能不能标定？ | 每 2 分钟一个窗口，各算 `k = ∫I dt / ΔCC`。变异系数 ≤3% 且已收敛 → 固定比例偏差，给标定系数 `1/k`；k 漂 → 随工况变，单一系数没意义 |

这样不用跑五遍：同一段物理过程，抽稀是事后做的，严格可比。空档按 3 倍采样间隔切块，积分与 ΔCC 都只在块内累加，绝不拿两端电流去插值空白段。

| 结果 | 含义 |
|---|---|
| 收敛 + k 稳定 | 电流读数是**固定比例偏差**，这段充电里乘 `1/k` 就能与库仑计对齐 |
| 收敛 + k 漂 | 偏差随 SOC / 温度 / 电流档变，标定无意义，得建模型或逐段测 |
| 不收敛 | 采样间隔仍在影响结果，先加密采样（或电流本身在剧烈跳变） |

**别把结论用过头**：基准是库仑计 ΔCC，不是绝对真值，库仑计自己也有标定误差；这里量的是两条独立路径的**一致性**。结论只保证「这台机器、这一段充电」成立，换充电器或换 SOC 区间要重测 —— App 里也写了这句。

## 精度

软件方案实际误差 **3–5%**，来源：

1. **库仑计标定**。厂商标定本身有偏差，换电池后可能不重新标。
2. **负载不恒定**。使用强度不同，电池实际输出容量略有差异。
3. **温度归一**。默认每 °C 0.2% 是经验系数，不是每块电池的真值。
4. **截止电压**。系统 0% 到真正欠压保护之间还有残余电量，各厂设置不同。
5. **SOC 折算**。跨度不足 100% 时假设区间内电荷均匀，SOC 本身只有 1% 分辨率。

想要 1% 以内的绝对精度，只有外部电子负载恒功率放电一条路。

## 暂不覆盖 iOS / 鸿蒙

不是不想做，是数据源不成立：

- **iOS**：没有公开的电流或库仑计接口。私有 API 上不了架；
  唯一可行的是「满电到关机的时长 × 平均功耗」，误差 10% 以上，不如不做。
- **鸿蒙 NEXT**：`@ohos.batteryInfo` 给的是健康状态枚举，不是可用容量；
  电流读数在多数设备上受限。真要做，前提是先拿到可用的电流或库仑计通道。

将来接入只需要新增一个采集后端输出同格式 CSV，分析端一行都不用改。
