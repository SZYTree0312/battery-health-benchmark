# bhbench — 安卓电池等效容量与健康度测量

用一次受控放电，算出手机电池**真实放出了多少电荷**，再和标称容量比对。
不看厂商那个百分比——那是各家算法的加权结果，权重不公开，跨品牌没法比。

手机上跑，不需要电脑、不需要 root。

```
等效容量   6574 mAh
标称容量   7000 mAh
健康度     93.9%   良好
数据来源   系统库仑计
```

---

## 两种用法

| 方式 | 适合谁 | 需要什么 |
|---|---|---|
| **装 App**（主推） | 普通使用：自己测自己的手机 | 一个 APK，装完拔线就能跑 |
| **adb 采集**（进阶） | 批量测多台、无界面环境、开发调试 | 电脑 + adb + 编译好的二进制 |

App 和 adb 走同一套数据源、同一套算法，CSV 格式一模一样，
所以两边结果可以互相验证。

## App 怎么用

```bash
adb install -r bhbench.apk
```

或者直接把 `bhbench.apk` 传到手机上点开安装。

**推荐流程：一次记录覆盖放电和充电**

1. 打开 App，填厂商标称容量，点**开始**——之后一直记录，中途不要停
2. 正常用手机。电量到 15% 左右 App 会弹提醒（也可以自己留意）
3. 插上原装充电器充到 100%，期间不用管 App
4. 拔线，点**分析最新**

一份 CSV 里同时有放电段和充电段，分析器会自动挑合格的那一段：

- 从 100% 用到 15% 的放电段**不完整**（没放到关机），会被跳过
- 改用 15%→100% 的充电段，按 SOC 跨度折算

**为什么不等到自动关机**：手机一关，App 就没了；插上充电器重新开机后需要解锁、
找图标、再点开始，这中间已经充进去几个点，误差反而更大。留 10–15% 插电是更优解。

如果你愿意完整放电（更准，不需要折算），就充满、拔线、用到自动关机，
中途同样不要停。放电段不需要任何假设，精度最高，代价是占用几个小时的使用时间。

测试期间可以正常用手机——库仑积分对负载波动免疫，只是结果代表你自己的使用强度。

结果页会给出：大号健康度 + 评级、三张指标卡（等效容量 / 标称 / 时长）、
明细（放出能量、平均电压电流、峰值温度、SOC 区间、数据来源、采样点），
以及这次测量存在的问题清单。数据不足时不给百分比，直接写「数据不足」。

底部「导出原始数据」走系统文件选择器，不申请存储权限——导出是附带功能，
主要出口是这个结果页。

App 里做了三件事保证数据能用：

- **前台服务 + 常驻通知**，避免跑几小时被系统或 ROM 的省电策略杀掉
- 只读公开 API（`BatteryManager` 的库仑计和电池广播），不 root、不碰 sysfs
- 每 5 秒落盘一次，关机最多丢 5 秒数据

### 自己编译

不需要 Gradle，也不需要 Android Studio。只要有 JDK 17 和 Android SDK
（`platforms;android-34` + `build-tools;34.0.0`）：

```bash
cd app && ./build-apk.sh
```

脚本走 `aapt2 → javac → d8 → zipalign → apksigner` 五步手工打包。
这个 App 零第三方依赖、界面用代码构建不写 XML，所以能这么干——
几秒出结果，任何一步失败都能直接看到是哪个环节。

## 为什么不用厂商的健康度

厂商显示的百分比大致由三样东西加权而来：容量衰减、循环次数、内阻上升。
权重各家不公开，还会随系统版本调整。结果就是：

- 同一块电池，A 品牌显示 92%，B 品牌显示 87%，实际容量可能一样
- 换过电池或第三方维修后，百分比可能完全不更新
- 出厂标定和实际容量本来就有 2–5% 的差

所以这个工具绕过所有厂商接口，自己做一次物理测量：从满电放到关机，
记录全程的电荷流出。两条数据通道择一：

1. **能读到电流** → 库仑积分（`sysfs` 可读的机型，或 adb 采集）
2. **只有库仑计** → 计数器首尾相减（小米等把 sysfs 封死的机型）

第二条不比第一条差：库仑计是累计量，首尾差直接就是放出电荷，
不经过积分，也不累积采样误差。实测这类机器的库仑计约 20–25 秒跳一次，
所以 5 秒采一次足够，跳变时刻不会漏。

## 三个部件

| 部件 | 语言 | 职责 |
|---|---|---|
| `app/` | Java（零依赖） | 手机端 App：采样、前台服务、出报告 |
| `collector-native/` | C++17 单文件 | adb 采集用，直读 sysfs 或调 `dumpsys` |
| `analyzer/` | Python 3.9+ | PC 端分析，与 App 内算法一致，可交叉校验 |
| `runner.py` | Python | adb 编排：probe / start / fetch / stop |
| `protocol/` | 文档 | 测量协议，固定温度、倍率、截止条件 |

数据流是单向的：设备只记原始时序，结论单独算。这条边界不能破——
一旦让手机自己"边采边算边修正"，各家 ROM 的省电策略就会混进结果里。

## adb 方式（批量 / 无界面）

```bash
cd collector-native && ./build.sh && cd ..   # 需要 NDK
python runner.py probe                        # 看这台机能读到什么
python runner.py start                        # 启动守护采集，命令返回后拔线
python runner.py fetch --design 7000          # 放电结束后取数据
```

关键点：手机插着 USB 就在充电、根本不会放电，所以采集必须能在拔线后继续跑。
`--daemon` 让程序自己 `fork + setsid` 脱离 adb 会话（`nohup` 和 `setsid`
命令实测都会被 shell 的进程组回收干掉）。

| 品牌 | sysfs 电流 | 库仑计（App 可用） | 备注 |
|---|---|---|---|
| 小米 / Redmi | 新机型全封 | 可用 | 25113PN0EC（HyperOS 17）实测 sysfs 0/8，App 走库仑计 |
| 一加 / realme | 通常可读 | 通常可用 | ColorOS 会杀后台，App 已用前台服务 |
| OPPO / vivo | 多数可读 | 多数可用 | 部分机型需 `adb root` 才能读 sysfs |
| 华为 / 荣耀 | 部分可读 | 多数可用 | EMUI 对 sysfs 限制较严 |
| 三星 | 通常可读 | 通常可用 | sysfs 最规整 |

读不到库仑计、也读不到电流的机型，整个方法就退化——没有电荷数据就没法算。

## 三法交叉校验（测试期）

现在有三种独立方法可以算容量，各自假设不同。测试期的目标不是"信哪一种"，
而是**用数据决定哪一种可信**：

| 方法 | 数据来源 | 成本 | 隐含假设 |
|---|---|---|---|
| **A 满电直读** | 充满时的库仑计读数 | 零（充电时自动记） | counter 是实测积分，不是标定常数 |
| **B 放电测量** | 满电 → 低电量的电荷积分 | 几小时使用时间 | 无（这是基准） |
| **C 充电折算** | 低电量 → 满电的充入量 ÷ SOC 跨度 | 一个晚上 | 电荷在 SOC 区间内均匀分布 |

App 会在每次充满时自动落一条快照，所以 A 是白送的；B 和 C 需要你手动开一次记录。

攒够数据后跑：

```bash
python analyzer/compare.py data/session_*.csv --design 7000 --snapshots data/snapshots.csv
```

它会给出三种方法的数值、互相偏差和置信度评级，并回答那个关键问题：

- **A 与 B 相差 < 2%** → counter 可信，以后充满读一次就够，整个流程可以砍到零成本
- **相差 2–5%** → 可做趋势参考，别当绝对容量
- **相差 > 5%** → counter 多半是标定常数，必须靠 B 或 C

置信度规则写在 `analyzer/compare.py` 里，可以直接改：

- B 要求起始 ≥95%、结束 ≤10%、时长 ≥2h，三条全满足才是「高」
- C 的误差模型是 `2% + 30/跨度`，跨度 85% 时约 ±2.4%，跨度 60% 时约 ±2.5%
- A 没有独立判据，只能用「和 B 的偏差」反推它可不可信

## 精度

软件方案实际误差 **3–5%**，来源：

1. **库仑计标定**。厂商标定本身有偏差，换电池后可能不重新标。
2. **负载不恒定**。使用强度不同，电池实际输出容量略有差异。
3. **温度归一**。默认每 °C 0.8% 是经验系数，不是每块电池的真值。
4. **截止电压**。系统 0% 到真正欠压保护之间还有残余电量，各厂设置不同。

想要 1% 以内的绝对精度，只有外部电子负载恒功率放电一条路。

## 暂不覆盖 iOS / 鸿蒙

不是不想做，是数据源不成立：

- **iOS**：没有公开的电流或库仑计接口。私有 API 上不了架；
  唯一可行的是「满电到关机的时长 × 平均功耗」，误差 10% 以上，不如不做。
- **鸿蒙 NEXT**：`@ohos.batteryInfo` 给的是健康状态枚举，不是可用容量；
  电流读数在多数设备上受限。真要做，前提是先拿到可用的电流或库仑计通道。

将来接入只需要新增一个采集后端输出同格式 CSV，分析端一行都不用改。
